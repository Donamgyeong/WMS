# WMS 전체 구조 설계

작성일: 2026-11-13 (Asia/Seoul) · 상태: 인증 기본 흐름 구현, 근태·임금 업무 기능 미구현

## 기준과 범위

근무 규칙은 [AGENTS.md](../AGENTS.md), 범위·단계·검증 시나리오는 [구현 계획](attendance-system-plan.md)을 따른다. 이 문서는 해당 로컬 문서를 기준으로 구조를 구체화하며, Notion 원문의 최신 내용을 재확인한 결과는 아니다. 미정 정책은 이 설계로 확정하지 않는다.

Next.js App Router + TypeScript, PostgreSQL, Drizzle ORM(node-postgres), Docker Compose를 사용한다. 하나의 앱과 DB 안에서 업무 모듈을 분리한다. 별도 마이크로서비스나 작업 큐는 현재 도입하지 않는다. 장시간 재계산·Excel 처리의 비동기 실행 방식은 데이터량과 운영 환경을 확인한 뒤 결정한다.

## 화면과 서버 진입점

| 제안 경로 | 기능 | 서버 접근 범위 |
| --- | --- | --- |
| `/me` | 출퇴근·휴게, 오늘 현황, 캘린더, 일·주·월 내역 | 본인 |
| `/team` | 부서원 현황, 주간 집계, 누락·위험 현황 | 담당 부서 |
| `/admin` | 조직·권한·근무지·정책·휴일·근태 관리 | 관리자 |
| `/admin/payroll` | 시급·계약·계산·정산·Excel | 관리자 |

향후 `(auth)`, `(employee)`, `(manager)`, `(admin)` 라우트 그룹으로 레이아웃을 나눈다. 그룹과 메뉴는 권한 검사 수단이 아니다. 화면·API는 기능 구현 시 생성하며 현재는 기존 초기 화면과 health API를 유지한다.

API는 `/api/attendance`, `/api/team`, `/api/admin`, `/api/admin/payroll` 아래 업무별로 추가한다. 상세 메서드·입력·출력·오류 계약은 해당 기능 착수 전에 정한다. 서버 페이지는 내부 HTTP 호출 대신 동일한 권한 검사를 수행하는 서비스를 호출할 수 있다.

## 디렉터리

```text
src/
  app/                    Next.js 페이지·레이아웃·API
  modules/                업무 모듈
    identity/             인증·역할·접근 범위
    organization/         직원·부서·소속 이력
    workplace/            근무지·IP·GPS 검증
    policy/               정책·적용 기간·미정 상태
    calendar/             휴일·개인 일정·휴가
    attendance/           원본 이벤트·정정 이력
    worktime/             세션·구간·시간 집계
    payroll/              시급·계약·임금 계산
    settlement/           정산 확정·버전·조정
    reporting/            보고서·Excel
    integrations/         외부 시스템 어댑터
  components/
    ui/                   공통 UI
    layout/               공통 화면 틀
  db/
    index.ts              서버 전용 DB 연결
    schema/index.ts       Drizzle 스키마 export 진입점
  shared/
    config/               환경 설정 검증
    errors/               공통 오류 표현
    time/                 공통 시간 표현·연산
drizzle/                  SQL·마이그레이션 메타데이터
tests/integration/       실제 DB·API·권한 검증
tests/e2e/               사용자 흐름 검증
docs/decisions/          기술 결정 기록
```

`drizzle/`은 기존 마이그레이션을 그대로 보존한다. 업무 테이블은 구현 시 `src/db/schema/`의 영역별 파일로 나누고 `index.ts`에서 명시적으로 export한다. 생성 SQL과 메타데이터는 검토·적용 후 함께 관리한다.

## 모듈 내부 책임과 의존 방향

필요한 경우에만 다음 파일 또는 하위 디렉터리를 만든다. 빈 계층을 일괄 생성하지 않는다.

- `domain`: DB·Next.js에 의존하지 않는 계산 규칙과 상태 전이.
- `service`: 인증된 사용자에 대한 권한·대상 범위 검사, 업무 순서, 트랜잭션 조정.
- `repository`: Drizzle 조회·저장. 요청에서 받은 직원·부서 ID를 그대로 신뢰하지 않는다.
- `validation`: 외부 입력 형식 검증. 권한·업무 규칙 검증을 대체하지 않는다.
- `*.test.ts`: 계산·상태 전이 단위 테스트.

기본 방향은 `app → service → domain/repository → db`다. 클라이언트 UI는 서버 서비스·DB·임금 계산 모듈을 import하지 않는다. 서버 전용 진입점은 `server-only`로 보호한다. 공통 UI와 shared는 업무 모듈에 의존하지 않는다. 근무정책 자체는 shared/time이 아닌 policy와 업무 domain에 둔다.

모듈 간 호출은 명시적인 서비스 또는 타입 계약을 사용하고, 다른 모듈의 repository를 직접 호출하지 않는다. attendance는 원본을 제공하고 worktime은 이를 읽어 파생 데이터를 만든다. payroll은 근로 구간과 정책·시급·계약 이력을 입력으로 계산한다. settlement는 계산 결과를 검토하고 확정한다. reporting은 권한별 조회 계약을 사용하며 임금 보고서는 관리자 전용으로 분리한다. 순환 의존이 생기면 서비스에서 처리 순서를 조정하거나 공통 계약을 추출한다.

## 데이터 흐름과 보존

1. 인증·접근 범위를 확인하고 PC IP 또는 모바일 GPS를 검증한다.
2. 중복 요청을 식별하며 출퇴근·휴게 원본 이벤트와 검증 결과를 저장한다.
3. 정정 이력을 반영해 세션·근로 구간을 계산한다. 비정상 순서와 누락은 상태로 남긴다.
4. 휴게를 제외한 실제 근로시간을 일·주·월로 집계한다.
5. 관리자 경로에서 정책·시급·계약의 적용 기간별로 임금을 계산한다.
6. 미정 정책·입력 누락을 검사한 뒤 정산을 확정하고 보고서·Excel을 제공한다.

원본 이벤트는 덮어쓰지 않고 정정을 별도 보존한다. 세션·구간은 재계산 가능한 파생 데이터로 관리한다. 입력 원본·정정·정책 버전·계산 버전을 추적하며 같은 입력에 같은 결과가 나와야 한다. 정산 라인에서 계산 근거 구간까지 추적할 수 있어야 한다. 확정 결과가 참조하는 근거는 이후 재계산으로 소실되지 않도록 버전 또는 스냅샷으로 보존한다.

정책·시급·계약의 적용 기간, 근로 구간 중복은 DB 제약과 트랜잭션으로 보장한다. 구체적인 범위 자료형·EXCLUDE 제약·삭제 규칙은 물리 설계에서 검토한다. 확정 스냅샷은 불변이며 이후 변경은 새 버전과 조정 이력으로 처리한다.

## 권한 및 임금 경계

일반 업무 테이블은 기본 스키마, 시급·계약·임금·정산 테이블은 `payroll` 스키마에 둔다. 스키마 분리만으로 접근 통제가 완성되지는 않는다. 서버 서비스와 관리자 API에서 역할을 검사하고, 직원·부서장 조회에는 허용된 필드만 응답한다. 비관리자 DTO에는 임금 필드를 포함하지 않는다.

본인·담당 부서 범위는 인증된 사용자와 서버 데이터로 결정한다. 보고서·Excel·직접 API 호출에도 동일한 검사를 적용한다. 인증 방식과 세션·현재 담당 부서 조회는 [인증 결정 기록](decisions/0001-authentication.md)에 따른다. 겸직·소속 변경의 과거 내역 조회와 운영 DB 계정 분리는 후속 결정 대상이다.

## 미정 정책과 계산 상태

휴일·야간·연장 플래그는 독립적으로 보존한다. 실제 연장시간, 포괄 포함시간, 추가 지급 대상 시간과 금액을 구분한다. `allocation_policy=UNDECIDED`이면 미확정 금액은 `NULL`로 반환하고 UI·Excel에서 미확정으로 표시한다. 0원으로 치환하지 않는다.

예를 들어 실제 연장 20시간은 포괄 포함 16시간과 추가 대상 4시간으로 시간 집계할 수 있지만, 일반·야간 배정 순서가 미정이면 추가 지급액을 확정할 수 없다. 계약 고정수당과 법정수당 비교 절차도 확정 조건에 포함해야 한다.

반차 휴게·연장 인정, 휴일 배율, 반올림 등 미정 정책의 영향을 받는 결과는 차단 사유와 함께 제공한다. 관련된 결과만 보류하며 가능한 실제 시간 집계는 유지한다. 정산 상태 `OPEN/CALCULATED/FINALIZED`와 별도로 확정 차단 사유를 관리하는 방안을 상세 설계한다.

## 구현 및 검증 순서

1. 인증·권한표·정책 결정 목록·API 계약을 설계한다.
2. 조직·근무지·정책·일정과 원본 이벤트의 스키마·마이그레이션을 구축한다.
3. 출근→휴게→퇴근→본인 실근로시간 조회를 첫 번째 완결된 흐름으로 구현한다.
4. 부서 집계와 관리자 운영 화면을 연결한다.
5. 임금 계산·정산·보고서를 구현한다. 정책 미정 시 금액 확정을 차단한다.
6. 정책과 외부 API 확인 후 휴가 연동·정정 승인·알림·정산 조정을 확장한다.

업무 기능마다 테스트 코드를 작성하고 실행한다. 순수 계산은 인접 단위 테스트, DB 제약·동시 요청·권한은 integration, 출퇴근 및 정산 핵심 흐름은 e2e에서 검증한다. 테스트 러너와 실행 스크립트는 첫 기능 구현 전에 결정한다. 현재 tests 디렉터리는 위치만 마련한 상태다.

중점 사례는 휴게 제외, 8시간·22시·자정·주/월·시급 변경 경계, 중복 요청, 누락 이벤트, 재계산 일관성, 비관리자 임금 접근 차단, 미정 금액과 0원의 구분, 확정 정산 불변성이다.

## 후속 결정 기록

`docs/decisions/`에 문제·선택지·결정·근거·영향을 기록한다. 아직 결정하지 않은 항목은 다음과 같다.

- 인증 기본 결정은 [인증 결정 기록](decisions/0001-authentication.md)에 반영했다. SSO·메일 복구·MFA·계정 관리 UI는 후속 대상이다.
- 운영 배포·백업·복구·비동기 작업 실행 방식.
- 기준 시간대·주 시작일·야간 종료·자정 이후 귀속일.
- GPS 정확도·허용 오차·프록시 신뢰 및 IP 판정.
- 중복 요청 키·누락 이벤트 처리·정정 승인.
- AGENTS.md에 열거된 임금·반차·휴일·경보·반올림·외부 연동 정책.

디렉터리 생성은 업무 기능·API·권한 통제의 구현 완료를 의미하지 않는다.
